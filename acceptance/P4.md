# P4 — 业务执行与交付：实施前验收标准

状态：PARTIAL / IMPLEMENTATION_NOT_ACCEPTED。标准先于P4代码、模型运行和Office文件生成建立。当前0.4.0-alpha.1原生applied，338本地回归及6项安装后原生SDK/目录检查通过；但无任何业务Worker运行或Office产物，且原生Windows沙箱下连固定`--version`都未启动进程，故Office及各交付项未通过。

前置：P0–P2已通过；P3仍PARTIAL。依据[用户确认的阶段例外](P3-stage-exception-approved.md)，仅推进不依赖缺失MCP Manager/安全委派接口的P4工作，不把P3改为通过。P5确定性Review Gate和P6产品验收不在本阶段提前认领。

## 已知边界和判定规则

- 已逐项核对现有资产manifest：上表10个主ID与其各3个Worker一一匹配，共40角色；不新造/别名复制Agent。最终方法/字段以原persona和Skills映射为准；源worker JSON schema缺字段时不把schema-valid误当业务完整。
- LBO/comps/Nike源二进制模板缺失继续`MISSING_SOURCE_ASSET`；可另做明确命名的有限、独立生成工作簿，但不能冒充源模板恢复或完整等价。
- 商业源未授权时只做明确TEST_ONLY或真正用户提供输入的运行；不暗自请求付费数据、模型猜财务数据或正式业务动作。
- 内部检查/复核要求继续保留；P5 Gate未实现时产物是DRAFT/REVIEW_REQUIRED，不可宣称已审批、已发布或可正式记账/交易/KYC签字。
- 每次真实运行保存不可变run ID、模型/工具/Worker事实与原始失败。产物创建、结构检查、重算、PDF转换、视觉验收分开记录，不用一个静态PASS替代全部。
- 任何关键项未通过时P4不标完成；本文件可追加实际结果，不回写删除初始失败，也不以用户P3阶段例外降低P4标准。

## 0.4.0-alpha.1 增量与阻断

- [源映射](<../docs/P4_BUSINESS_MAP.md>)与[机器记录](P4-business-source-map.json)：363归档文件SHA、40角色、10×3 Worker归属二次核对零差异；141条文件/行号引用有效。两处业务纠正（statement-auditor=LP资本账户批次核对；valuation-reviewer=GP季末marks/NAV/carry）已写入标准与模板。
- [10种任务输入模板](<../docs/P4_TASK_TEMPLATES.md>)为纯函数SDK：17项测试、公开导出`./business-task-templates/v1`，[TAP](P4-task-template-tests.tap)。通过仅代表输入结构声明合法，明确不代表文件存在、SHA、授权、来源或Office已完成。
- 两个源检查数值库：[GL](<../docs/P4_GL_CHECKS.md>)精确cents/18dp数量与FX、全外连接六桶、不推断原因；[LP](<../docs/P4_LP_CHECKS.md>)精确有理数所有权、逐行0.01、基金NAV仅在完整LP集与显式来源容差下核对。二者均为本地库，非原生Tool。
- [338项本地回归](P4-regression-002.tap)0失败；[6项安装后原生检查](P4-native-candidate-health-001.json)确认10/30目录、绑定null/19、策略revision8及三个SDK可导入。无模型或Worker调用。
- Office原生探针连续失败并按序保留：[001](P4-office-native-failure-001.json)/[002](P4-office-native-failure-002.json)依赖解析、[003](P4-office-package-preparation-failure-003.json)包准备超时、[004](P4-office-native-failure-004.json)/[005](P4-office-native-failure-005.json)进程启动、[006](P4-native-startup-matrix-006.json)最小矩阵。已确立：固定`--version`在原生Windows ACL封装下即以3221225794退出，早于任何Office逻辑；未确立底层原因，未改用无沙箱执行、未替换引擎。
- 两项对照排除了解释并缩小结论：[007 环境对照](P4-office-env-control-007.json)四次同参数调用（覆盖/继承环境）全部同一状态码；[008 读取范围对照](P4-office-confinement-read-control-008.json)连`C:\Windows\System32\cmd.exe`也以同一状态码、空stdout/stderr退出。合计6次固定调用均`0xC0000142`，故既非环境替换、也非解释器所在路径不可读，而是**本机原生受限子进程启动路径本身不可用**。未以无沙箱方式重试。
- 同时核对当前Host公开契约：`ctx.fs`无`writeBytes`/二进制发布，`ctx.subprocess`无Agent/策略字段，`ctx.officeToPdf`只做已存在Office源的PDF转换。因此插件端既不能启动Office生产者，也不能把二进制产物写入工作区；这是独立于P3 MCP缺口的**第二个宿主接口缺口**，需宿主提供受支持的二进制产物写入或可用受限子进程后才能做Agent驱动的Office交付。`ctx.attachments`虽能存二进制，但属附件存储、非工作区成果，不冒充交付路径。
- 结论：P4仍PARTIAL。缺少十项原生业务运行、Office生成/重算/PDF、原生业务Tool注册与await后权限复验、只读Office结构检查；P3的Manager与安全MCP委派缺口不变。
